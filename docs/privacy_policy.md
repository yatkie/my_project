## 1. Purpose

Метою політики конфіденційності є визначення правил отримання, обробки, зберігання, передавання та видалення даних у програмному проєкті SolanaTokenManager.

Політика спрямована на:

- Захист конфіденційних даних користувача.
- Запобігання розкриттю приватних ключів.
- Мінімізацію обсягу оброблюваних даних.
- Забезпечення безпечної взаємодії із зовнішніми сервісами.
- Інформування користувача про особливості обробки даних у блокчейні Solana.

## 2. Scope

Політика конфіденційності поширюється на:

- Генерацію криптографічних ключових пар.
- Створення та ініціалізацію SPL-токенів.
- Випуск та підготовку переказу токенів.
- Формування та підписання транзакцій.
- Взаємодію з RPC-серверами Solana.
- Обробку конфігураційних та технічних даних.
- Журналювання операцій, якщо воно реалізоване.

Політика не регулює внутрішні процеси обробки даних сторонніми RPC-провайдерами та інфраструктурою блокчейну Solana.

## 3. Data Categories

### 3.1 Public Data

| Категорія | Опис |
| --- | --- |
| Public Key | Публічна адреса гаманця Solana. |
| Mint Address | Адреса створеного SPL-токена. |
| Token Account | Адреса облікового запису токенів. |
| Transaction Signature | Ідентифікатор підписаної транзакції. |
| Token Amount | Кількість токенів у публічній транзакції. |
| Token Decimals | Кількість десяткових знаків токена. |

Ці дані можуть бути доступними через блокчейн Solana після виконання відповідних операцій.

Публічність адреси гаманця не виключає можливості її пов'язування з конкретною особою.

### 3.2 Confidential Data

| Категорія | Опис |
| --- | --- |
| Private Key | Приватний криптографічний ключ користувача. |
| Keypair | Криптографічна ключова пара, що містить приватний ключ. |
| RPC API Key | Ключ доступу до RPC-сервісу, якщо використовується. |
| Secret Configuration | Конфігураційні дані, що містять секретну інформацію. |
| Unsigned Transaction | Параметри транзакції до її публікації. |

Конфіденційні дані повинні бути захищені від несанкціонованого доступу, копіювання та розкриття.

### 3.3 Technical Data

До технічних даних можуть належати:

- Адреса RPC-сервера.
- Обрана мережа Solana.
- Статус виконання операції.
- Повідомлення про помилки.
- Час виконання операцій.
- Інформація про версію програмного забезпечення.

### 3.4 Personal Data

Поточна специфікація проєкту не передбачає цілеспрямованого збору таких персональних даних:

- Ім'я та прізвище.
- Адреса електронної пошти.
- Номер телефону.
- Домашня адреса.
- Паспортні дані.
- Паролі облікових записів користувачів.
- Банківські реквізити.

Система не передбачає реєстрації користувачів або ведення централізованої бази їхніх персональних даних.

## 4. Data Sources

Дані можуть надходити з таких джерел:

| Джерело | Дані |
| --- | --- |
| Користувач | Адреси гаманців, кількість токенів та параметри операцій. |
| Solana SDK | Згенеровані криптографічні ключові пари. |
| RPC Server | Баланси, статуси транзакцій та інформація про облікові записи. |
| Solana Blockchain | Публічні дані про токени та транзакції. |
| Local Configuration | Налаштування мережі та параметри підключення. |

Усі дані, отримані із зовнішніх джерел, повинні перевірятися перед використанням.

## 5. Purpose of Data Processing

Дані обробляються виключно для виконання функціональних завдань SolanaTokenManager:

- Генерації криптографічних ключових пар.
- Створення Mint Account.
- Ініціалізації SPL-токенів.
- Отримання адрес Associated Token Account.
- Випуску токенів.
- Підготовки та виконання передбачених транзакцій.
- Перевірки статусу транзакцій.
- Обробки помилок програмного забезпечення.

Забороняється використовувати отримані дані для рекламних цілей, несанкціонованого профілювання користувачів або продажу третім сторонам.

## 6. Data Storage

### 6.1 Local Storage

Конфіденційні дані повинні оброблятися у локальному середовищі користувача.

Встановлюються такі вимоги:

- Приватні ключі не повинні зберігатися у вихідному коді.
- Приватні ключі не повинні потрапляти до Git-репозиторію.
- Файли із секретними даними повинні мати обмежені права доступу.
- Секретні конфігураційні файли повинні виключатися з Git за допомогою `.gitignore`.
- Постійне зберігання приватних ключів допускається лише за необхідності та із застосуванням належного захисту.

### 6.2 Memory Storage

Під час виконання криптографічних операцій приватні ключі можуть тимчасово перебувати в оперативній пам'яті.

Час перебування секретних даних у пам'яті повинен бути мінімізований.

За можливості необхідно застосовувати підтримувані бібліотеками механізми очищення секретних даних після завершення операції.

### 6.3 Blockchain Storage

Після підтвердження транзакції відповідна інформація записується до блокчейну Solana.

До таких даних можуть належати:

- Публічні адреси гаманців.
- Адреси токенів.
- Кількість переданих або випущених токенів.
- Ідентифікатори транзакцій.
- Інформація про виконані інструкції.

Приватні ключі не повинні записуватися до блокчейну.

### 6.4 Database Storage

Поточна архітектура проєкту не передбачає використання бази даних для зберігання персональних даних або історії операцій користувачів.

## 7. Access Control

Доступ до конфіденційних даних повинен надаватися за принципом мінімально необхідних привілеїв.

| Суб'єкт | Доступ |
| --- | --- |
| User | Власні ключі та параметри операцій. |
| SolanaTokenManager | Дані, необхідні для виконання поточної операції. |
| RPC Server | Підписані транзакції та необхідні RPC-запити. |
| Solana Blockchain | Публічні дані транзакцій. |
| AI Agent | Лише знеособлені або тестові дані. |
| Third Parties | Доступ до секретних даних заборонений. |

Приватні ключі не повинні передаватися стороннім компонентам, які не потребують їх для локального підписання транзакцій.

## 8. Data Sharing and Transfer

### 8.1 RPC Communication

Для взаємодії з мережею Solana застосунок використовує RPC-з'єднання.

RPC-серверу можуть передаватися:

- Публічні адреси гаманців.
- Адреси токенів.
- Параметри RPC-запитів.
- Підписані транзакції.
- Ідентифікатори транзакцій.

Передавання приватних ключів RPC-серверу заборонено.

Для віддалених RPC-з'єднань необхідно використовувати HTTPS із перевіркою TLS-сертифікатів.

### 8.2 Blockchain Communication

Підписані транзакції передаються до мережі Solana через RPC-сервер.

Користувач повинен враховувати, що дані підтверджених транзакцій можуть бути доступними іншим учасникам мережі.

Забороняється включати секретні або непотрібні персональні дані до інструкцій транзакцій.

### 8.3 Third-Party Services

RPC-провайдери можуть отримувати технічну інформацію про мережеві підключення, зокрема IP-адреси та параметри запитів.

Обробка таких даних сторонніми сервісами регулюється їхніми власними політиками конфіденційності.

У разі додавання нових зовнішніх інтеграцій політика конфіденційності повинна бути переглянута.

## 9. Data Retention

Встановлюються такі правила зберігання даних:

| Категорія | Строк зберігання |
| --- | --- |
| Тимчасові приватні ключі | До завершення необхідних криптографічних операцій. |
| Постійні ключі користувача | До моменту їх видалення або заміни користувачем. |
| Тимчасові параметри транзакцій | До завершення операції та перевірки її результату. |
| Локальні технічні журнали | Не більше 30 днів, якщо журналювання реалізоване. |
| Конфігураційні дані | Протягом періоду використання застосунку. |
| Дані блокчейну | Відповідно до механізмів зберігання мережі Solana. |

Дані не повинні зберігатися довше, ніж це необхідно для визначеної мети їх обробки.

## 10. Data Deletion

Користувач може видаляти локальні файли, конфігурацію та журнали, створені застосунком.

Під час видалення конфіденційних даних необхідно:

- Припинити використання відповідних секретних даних.
- Видалити непотрібні локальні файли.
- Перевірити наявність копій секретних даних.
- У разі компрометації ключа перенести активи або повноваження на новий ключ, якщо це можливо.

Видалення локального приватного ключа не видаляє відповідний обліковий запис із блокчейну та може призвести до втрати доступу до активів.

SolanaTokenManager не може видаляти або змінювати історію підтверджених транзакцій у блокчейні Solana.

## 11. Logging

Журналювання повинно використовуватися лише для діагностики помилок та контролю виконання операцій.

### 11.1 Allowed Logging

Дозволяється записувати:

- Час виконання операції.
- Тип операції.
- Статус виконання.
- Ідентифікатор транзакції.
- Технічні повідомлення про помилки.
- Інформацію про недоступність RPC-сервера.

### 11.2 Prohibited Logging

Забороняється записувати:

- Приватні ключі.
- Повний секретний вміст криптографічних ключових пар.
- Seed-фрази, якщо їх підтримка буде додана.
- Паролі.
- RPC API-ключі.
- Токени доступу.
- Повний вміст секретних конфігураційних файлів.

Повідомлення про помилки не повинні розкривати конфіденційні дані.

## 12. Cryptographic Protection

Для захисту конфіденційних даних встановлюються такі вимоги:

- Використання підтримуваних криптографічних бібліотек Solana SDK.
- Генерація ключових пар із використанням криптографічно безпечних механізмів.
- Локальне підписання транзакцій.
- Використання HTTPS для віддалених RPC-з'єднань.
- Захищене зберігання приватних ключів у разі необхідності їх постійного зберігання.
- Заборона самостійної реалізації криптографічних алгоритмів.
- Заборона передавання приватних ключів через мережу.

## 13. Data Minimization

SolanaTokenManager повинен обробляти лише ті дані, які необхідні для виконання його функціональних завдань.

Забороняється:

- Збирати непотрібні персональні дані.
- Створювати необґрунтовані копії приватних ключів.
- Зберігати зайві конфіденційні дані.
- Передавати стороннім сервісам інформацію, яка не потрібна для виконання операції.
- Використовувати реальні секретні дані у тестах та документації.

Для розробки та тестування необхідно використовувати тестові ключові пари та мережу Solana Devnet.

## 14. User Rights and Responsibilities

Користувач має право:

- Контролювати власні приватні ключі.
- Отримувати інформацію про категорії оброблюваних даних.
- Переглядати та видаляти локальні дані.
- Припинити використання програмного забезпечення.
- Самостійно обирати довірений RPC-сервер у межах підтримуваної конфігурації.

Користувач повинен:

- Забезпечувати конфіденційність власних приватних ключів.
- Перевіряти параметри транзакцій перед їх виконанням.
- Не передавати секретні дані стороннім особам.
- Використовувати довірені RPC-сервери.
- Враховувати публічність даних блокчейну.
- Забезпечувати безпечне зберігання резервних копій ключів за необхідності.

- Додавання бази даних.
- Зміна механізмів зберігання приватних ключів.
- Виявлення загроз конфіденційності.
