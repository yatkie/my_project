# Access Control Policy



## 1. Purpose



Метою документа є визначення моделі керування доступом,

ролей користувачів, захищених ресурсів та правил авторизації

у програмному забезпеченні SolanaTokenManager.



## 2. Access Control Model



Для програмного проєкту SolanaTokenManager обрано рольову

модель керування доступом (Role-Based Access Control, RBAC).



Права доступу призначаються ролям, а користувач отримує

відповідні дозволи після успішної автентифікації.



Вибір RBAC обґрунтовано такими перевагами:



- Простота реалізації та супроводу.

- Централізоване визначення прав доступу.

- Розмежування повноважень користувачів.

- Дотримання принципу мінімальних привілеїв.

- Можливість подальшого розширення системи.



## 3. Subjects



Суб'єктами доступу є користувачі програмного забезпечення.



Передбачено три ролі:



### Admin



Адміністратор має повний доступ до передбачених

моделлю операцій системи.



### Operator



Оператор має обмежений доступ до операцій підготовки

створення та ініціалізації SPL-токенів.



Оператор не має права випускати токени та підписувати

транзакції.



### Viewer



Користувач має право лише переглядати неконфіденційну

інформацію про систему.



Неавтентифіковані користувачі не мають доступу

до захищених операцій.



## 4. Protected Resources



До захищених ресурсів системи належать:



- Криптографічні ключові пари.

- Mint Account.

- SPL-токени.

- Associated Token Account.

- Інструкції випуску токенів.

- Транзакції Solana.

- Інформація про стан системи.



Приватні ключі та паролі не повинні виводитися

у консоль або передаватися стороннім особам.



## 5. Subject and Object Attributes



Для прийняття рішення про доступ використовуються

такі характеристики суб'єкта:



- Стан автентифікації користувача.

- Призначена користувачу роль.

- Набір дозволів відповідної ролі.



Характеристики об'єкта доступу:



- Тип ресурсу.

- Тип запитуваної операції.

- Необхідний дозвіл для виконання операції.



Рішення про доступ приймається на основі відповідності

дозволів ролі вимогам захищеної операції.



## 6. Permissions



У системі передбачено такі дозволи:



| Permission | Description |

| --- | --- |

| ViewInfo | Перегляд інформації про систему |

| GenerateKeys | Генерування криптографічних ключів |

| CreateMint | Підготовка створення Mint Account |

| InitializeMint | Підготовка ініціалізації SPL-токена |

| CreateTokenAccount | Підготовка Associated Token Account |

| MintTokens | Підготовка випуску токенів |

| SignTransaction | Формування та підписання транзакції |



## 7. Access Control Matrix



| Operation | Admin | Operator | Viewer | Unauthenticated |

| --- | --- | --- | --- | --- |

| ViewInfo | Allow | Allow | Allow | Deny |

| GenerateKeys | Allow | Allow | Deny | Deny |

| CreateMint | Allow | Allow | Deny | Deny |

| InitializeMint | Allow | Allow | Deny | Deny |

| CreateTokenAccount | Allow | Allow | Deny | Deny |

| MintTokens | Allow | Deny | Deny | Deny |

| SignTransaction | Allow | Deny | Deny | Deny |



## 8. Authorization Rules



У системі застосовуються такі правила авторизації:



1. Доступ надається лише після успішної автентифікації.

2. Роль визначається на основі довіреної конфігурації

   облікового запису.

3. Користувач не може самостійно підвищувати свою роль.

4. Кожна роль має визначений набір дозволів.

5. Перевірка дозволу виконується безпосередньо перед

   виконанням захищеної операції.

6. За відсутності необхідного дозволу операція

   не виконується.

7. Невідомі ролі та непередбачені дозволи відхиляються.

8. За замовчуванням доступ заборонено.

9. Приховування пунктів меню не замінює перевірку прав.

10. Після завершення програми сеанс припиняється.



## 9. Authorization Process



Процес авторизації складається з таких етапів:



1. Запуск програмного забезпечення.

2. Автентифікація користувача.

3. Визначення ролі користувача.

4. Формування контексту поточного користувача.

5. Запит на виконання операції.

6. Визначення необхідного дозволу.

7. Перевірка прав користувача.

8. Надання або відмова у доступі.



У разі відсутності необхідного дозволу система

повинна повідомити:



Access denied: insufficient permissions.



## 10. Security Principles



Під час реалізації механізму керування доступом

застосовуються такі принципи:



- Least Privilege — мінімальні привілеї.

- Deny by Default — заборона доступу за замовчуванням.

- Complete Mediation — перевірка кожної захищеної операції.

- Separation of Duties — розмежування повноважень.

- Defense in Depth — багаторівневий захист.



## 11. Implementation



Для реалізації рольової моделі передбачається

використання таких файлів:



| File | Purpose |

| --- | --- |

| src/auth.rs | Автентифікація користувачів |

| src/access_control.rs | Ролі, дозволи та перевірка прав |

| src/main.rs | Виконання захищених операцій |

| docs/access_control.md | Документація моделі доступу |



Автентифікація базується на алгоритмі bcrypt,

реалізованому в межах лабораторної роботи №4.



Роль користувача повинна бути пов'язана з його

обліковими даними, а не визначатися довільним

введенням ролі після входу.



Перевірка прав повинна виконуватися всередині

функцій захищених операцій.



## 12. Security Testing



Для перевірки механізму авторизації передбачено

такі сценарії тестування:



| ID | Scenario | Expected Result |

| --- | --- | --- |

| TC-01 | Admin переглядає інформацію | Allow |

| TC-02 | Admin генерує ключі | Allow |

| TC-03 | Admin готує створення токена | Allow |

| TC-04 | Admin готує випуск токенів | Allow |

| TC-05 | Admin підписує транзакцію | Allow |

| TC-06 | Operator переглядає інформацію | Allow |

| TC-07 | Operator генерує ключі | Allow |

| TC-08 | Operator готує створення токена | Allow |

| TC-09 | Operator готує випуск токенів | Deny |

| TC-10 | Operator підписує транзакцію | Deny |

| TC-11 | Viewer переглядає інформацію | Allow |

| TC-12 | Viewer генерує ключі | Deny |

| TC-13 | Viewer готує створення токена | Deny |

| TC-14 | Viewer підписує транзакцію | Deny |

| TC-15 | Неавтентифікований користувач виконує операцію | Deny |

| TC-16 | Користувач намагається підвищити свою роль | Deny |

| TC-17 | Прямий виклик захищеної функції без дозволу | Deny |

| TC-18 | Використання невідомої ролі | Deny |



Для запуску модульних тестів використовується команда:



    cargo test



Фактичні результати тестування фіксуються після

реалізації механізму авторизації.

## 15. Conclusion



Для програмного забезпечення SolanaTokenManager

розроблено рольову модель керування доступом RBAC.



Визначено суб'єкти, захищені ресурси, ролі користувачів,

дозволи, матрицю доступу та правила авторизації.



Запропонована модель забезпечує розмежування повноважень

відповідно до принципу мінімальних привілеїв.



Документ є основою для програмної реалізації та

тестування механізму керування доступом у межах

лабораторної роботи №5.
