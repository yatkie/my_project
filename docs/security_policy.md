## 1. Purpose

Метою політики безпеки є встановлення обов'язкових правил безпечної розробки, тестування, експлуатації та супроводу програмного проєкту SolanaTokenManager.

Основними цілями політики є:

- Захист приватних ключів користувача.
- Забезпечення цілісності транзакцій.
- Безпечна взаємодія з мережею Solana через RPC.
- Запобігання несанкціонованому випуску та переказу токенів.
- Захист вихідного коду та конфігурації проєкту.
- Забезпечення доступності програмного забезпечення.
- Своєчасне виявлення та усунення вразливостей.

## 2. Scope

### 2.1 Included Scope

Політика безпеки поширюється на:

- Вихідний код у директорії `src/`.
- Документацію у директорії `docs/`.
- GitHub-репозиторій проєкту.
- Конфігураційні файли `Cargo.toml` та `Cargo.lock`.
- Зовнішні бібліотеки та залежності Rust.
- Генерацію криптографічних ключових пар.
- Створення та ініціалізацію SPL-токенів.
- Випуск та підготовку переказу токенів.
- Формування та підписання транзакцій.
- Взаємодію з мережею Solana через RPC.
- Середовище розробки та тестування.

### 2.2 Excluded Scope

До області дії політики не належать:

- Внутрішня інфраструктура блокчейну Solana.
- Внутрішня інфраструктура сторонніх RPC-серверів.
- Реєстрація та авторизація користувачів.
- Зберігання історії операцій у базі даних.
- Інтеграція з Pump.fun, яка ще не реалізована.
- Повноцінний графічний інтерфейс.

| --- | --- |
| Project Owner | Затвердження політики безпеки, контроль ризиків та погодження винятків. |
| Developer | Безпечна реалізація функціональності, тестування та усунення вразливостей. |

Оскільки проєкт є індивідуальним, ролі власника, розробника та рев'юера можуть виконуватися однією особою.

ШІ-агенти не повинні отримувати доступ до реальних приватних ключів, паролів та інших секретних даних.

## 4. Security Principles

Під час розробки проєкту необхідно дотримуватися таких принципів:

- **Least Privilege** — використання мінімально необхідних привілеїв.
- **Defense in Depth** — застосування декількох рівнів захисту.
- **Secure by Default** — використання безпечних налаштувань за замовчуванням.
- **Fail Securely** — безпечне завершення операцій у разі виникнення помилок.
- **Minimize Attack Surface** — мінімізація кількості потенційно небезпечних компонентів.
- **Input Validation** — перевірка всіх зовнішніх вхідних даних.
- **No Secrets in Source Code** — заборона зберігання секретних даних у вихідному коді.
- **Explicit Trust Boundaries** — визначення меж довіри між локальним застосунком та зовнішніми сервісами.

Для розробки та тестування за замовчуванням повинна використовуватися тестова мережа Solana Devnet.

## 5. Secure Development Environment

### 5.1 Repository Security

- Доступ на внесення змін до репозиторію надається лише уповноваженим особам.
- Для облікового запису GitHub необхідно використовувати двофакторну автентифікацію.
- Зміни вихідного коду повинні перевірятися перед інтеграцією в основну гілку.
- Коміти повинні містити зрозумілий опис внесених змін.
- Забороняється завантажувати до репозиторію приватні ключі та інші секретні дані.

### 5.2 Secret Management

- Приватні ключі не повинні зберігатися у вихідному коді.
- Файли із секретними даними повинні виключатися з Git за допомогою `.gitignore`.
- Секретні дані не повинні передаватися стороннім сервісам або ШІ-агентам.
- У разі компрометації приватного ключа необхідно припинити його використання та перенести активи або повноваження на новий ключ, якщо це можливо.

### 5.3 Dependency Management

- Зовнішні залежності повинні отримуватися з довірених джерел.
- Залежності проєкту повинні контролюватися через Cargo.
- Файл `Cargo.lock` повинен зберігатися у репозиторії.
- Перед додаванням бібліотеки необхідно перевірити її походження, актуальність та відомі вразливості.
- Залежності повинні регулярно перевірятися за допомогою `cargo audit`.

### 5.4 Development Environment

- Середовище розробки повинно регулярно оновлюватися.
- Для тестування необхідно використовувати тестові ключові пари.
- Забороняється використовувати гаманці з реальними активами для звичайного тестування.
- Перед виконанням транзакцій необхідно перевіряти обрану мережу Solana.

## 6. Software Protection

Для захисту програмного забезпечення встановлюються такі вимоги:

- Вихідний код повинен зберігатися у Git-репозиторії.
- Зміни конфігурації та програмного коду повинні відстежуватися через Git.
- Доступ на внесення змін повинен бути обмежений.
- Необхідно підтримувати актуальну копію вихідного коду у віддаленому репозиторії.
- Програмні збірки не повинні містити приватних ключів та інших секретних даних.
- Перед створенням релізу необхідно перевіряти його вихідний код та залежності.
- Забороняється публікувати конфіденційні дані у документації, журналах та програмних артефактах.

## 7. Secure Implementation

### 7.1 Input Validation

Усі зовнішні вхідні дані повинні вважатися недовіреними.

Необхідно перевіряти:

- Коректність публічних адрес Solana.
- Коректність адреси Mint Account.
- Коректність адреси отримувача токенів.
- Допустимість кількості токенів.
- Допустимість кількості десяткових знаків токена.
- Відсутність арифметичного переповнення.
- Коректність параметрів RPC-з'єднання.

У разі отримання некоректних даних операція повинна припинятися з відповідним повідомленням про помилку.

### 7.2 Cryptographic Security

- Для криптографічних операцій необхідно використовувати підтримувані бібліотеки Solana SDK.
- Забороняється самостійна реалізація криптографічних алгоритмів.
- Ключові пари повинні генеруватися з використанням криптографічно безпечних механізмів.
- Приватні ключі не повинні передаватися RPC-серверу.
- Підписання транзакцій повинно виконуватися локально.
- Доступ до приватних ключів повинен бути обмежений.

### 7.3 Transaction Security

Перед підписанням та відправленням транзакції необхідно перевіряти:

- Адресу відправника.
- Адресу отримувача.
- Кількість токенів.
- Адресу Mint Account.
- Ідентифікатори програм Solana, що використовуються.
- Наявність необхідних повноважень для виконання операції.
- Достатність балансу для виконання операції.
- Обрану мережу Solana.

Операції у Mainnet повинні виконуватися лише після явного підтвердження параметрів.

Після відправлення транзакції необхідно перевіряти її статус.

Забороняється автоматично створювати повторну транзакцію без перевірки результату попередньої операції.

### 7.4 Access Control

- Випуск токенів повинен виконуватися лише за наявності відповідних повноважень Mint Authority.
- Переказ токенів повинен виконуватися лише за наявності необхідних повноважень власника або уповноваженого підписанта.
- Операції повинні використовувати лише необхідні ключі та повноваження.
- Забороняється обходити механізми перевірки підписів Solana.

### 7.5 Network Security

- Необхідно використовувати довірені RPC-сервери.
- Для віддалених RPC-з'єднань необхідно використовувати HTTPS.
- Забороняється вимикати перевірку TLS-сертифікатів.
- Мережеві запити повинні мати обмежений час очікування.
- Повторні мережеві запити повинні бути обмежені.
- Відповіді RPC-сервера повинні перевірятися перед використанням.

### 7.6 Error Handling and Logging

- Помилки повинні оброблятися за допомогою механізмів `Result` та `Option`, де це доречно.
- Необхідно уникати використання `unwrap()` та `expect()` для недовірених даних.
- Помилки не повинні призводити до неконтрольованого завершення програми.
- Повідомлення про помилки повинні бути зрозумілими.
- Приватні ключі, паролі та інші секретні дані не повинні записуватися у журнали.
- Дозволяється журналювання статусів операцій, ідентифікаторів транзакцій та технічних помилок без розкриття секретних даних.

## 8. Security Verification

Перед інтеграцією змін необхідно виконувати такі перевірки:

| Перевірка | Інструмент |
| --- | --- |
| Перевірка компіляції | `cargo check` |
| Форматування коду | `cargo fmt --check` |
| Статичний аналіз | `cargo clippy` |
| Автоматизоване тестування | `cargo test` |
| Перевірка залежностей | `cargo audit` |
| Ручна перевірка коду | Code Review |
| Перевірка транзакцій | Solana Devnet |

Необхідно тестувати:

- Обробку некоректних адрес.
- Обробку некоректної кількості токенів.
- Недостатній баланс.
- Недостатність повноважень для виконання операцій.
- Недоступність RPC-сервера.
- Помилки підписання транзакцій.
- Невдалі транзакції.
- Запобігання повторному виконанню операцій.

Наявність невиправлених критичних вразливостей блокує випуск програмного забезпечення.

## 9. Vulnerability Management

Виявлені вразливості повинні реєструватися, аналізуватися та усуватися.

Для кожної вразливості необхідно визначити:

- Ідентифікатор.
- Опис проблеми.
- Уражений компонент.
- Потенційні наслідки.
- Рівень критичності.
- Спосіб усунення.
- Статус виправлення.

### 9.1 Vulnerability Classification

| Рівень | Опис | Цільовий строк усунення |
| --- | --- | --- |
| Critical | Компрометація приватних ключів або несанкціоновані операції з активами. | 24 години |
| High | Серйозне порушення цілісності або безпеки системи. | 7 днів |
| Medium | Обмежене порушення безпеки або доступності. | 14 днів |
| Low | Незначні проблеми безпеки. | 30 днів |

### 9.2 Vulnerability Resolution

Процес усунення вразливостей включає:

1. Виявлення та реєстрацію проблеми.
2. Оцінювання критичності.
3. Визначення способу виправлення.
4. Внесення змін до програмного коду.
5. Повторне тестування.
6. Оновлення документації та моделі загроз за необхідності.
7. Закриття запису про вразливість.

Інформація про невиправлені вразливості не повинна публікуватися разом із секретними даними або деталями, що створюють додатковий ризик.

## 10. Privacy Policy

- Публічні адреси гаманців.
- Приватні ключі.
- Адреси токенів.
- Параметри транзакцій.
- Ідентифікатори транзакцій.

Детальні правила обробки та захисту даних визначені в окремому документі [Privacy Policy](privacy_policy.md).

## 14. Symmetric Cryptographic Protection

### 14.1. Дані, що підлягають захисту

У проєкті SolanaTokenManager до найбільш чутливих даних належать:
- Приватний ключ гаманця Payer.
- Приватний ключ гаманця Mint.
- Ключ AES-256, який використовується для шифрування приватних ключів.

Публічні адреси гаманців та ідентифікатори транзакцій не потребують шифрування, оскільки є загальнодоступними.

### 14.2. Алгоритм шифрування

Для симетричного криптографічного захисту приватних ключів використовується AES-256-GCM.

Криптографічні параметри:
- Алгоритм: AES-256-GCM.
- Довжина ключа: 256 біт (32 байти).
- Довжина Nonce: 96 біт (12 байт).
- Довжина тегу автентифікації: 128 біт (16 байт).
- Генерація Nonce: криптографічно стійкий генератор випадкових чисел.

AES-GCM забезпечує конфіденційність, цілісність та автентичність зашифрованих даних.

### 14.3. Процес шифрування та розшифрування

Шифрування виконується перед записом приватних ключів гаманців у локальні файли.

Процес шифрування:
1. Генерується або отримується ключова пара Solana.
2. Приватний ключ перетворюється на масив байтів.
3. Дані шифруються алгоритмом AES-256-GCM.
4. Для кожної операції генерується новий випадковий Nonce.
5. Nonce та шифротекст із тегом автентифікації записуються у файл.

Розшифрування виконується під час завантаження гаманця для підготовки та підписання транзакцій. Програма зчитує зашифрований файл, отримує Nonce та виконує розшифрування з перевіркою автентичності даних.

### 14.4. Управління ключами шифрування

Ключ AES-256 передається програмі через змінну середовища `APP_ENCRYPTION_KEY_HEX`.

Вимоги до управління ключем:
- Ключ повинен мати довжину 32 байти.
- Ключ передається у шістнадцятковому форматі HEX.
- Забороняється зберігати ключ у вихідному коді.
- Забороняється додавати ключ до Git-репозиторію.
- Ключ повинен зберігатися окремо від зашифрованих файлів гаманців.
- Доступ до ключа повинен бути обмежений.

Наразі програма отримує ключ зі змінної середовища. Безпечне надання, резервне копіювання та ротація ключа є операційними процедурами.

### 14.5. Зберігання зашифрованих даних

Зашифровані файли гаманців зберігаються локально:

- `secrets/payer.enc`
- `secrets/mint.enc`

Директорія `secrets/` та файли з розширенням `.enc` виключені з Git за допомогою `.gitignore`.

У файлах зберігаються лише зашифровані дані. Відкриті приватні ключі використовуються в оперативній пам'яті лише під час необхідних криптографічних операцій.

### 14.6. Ротація ключів

Ротація ключа шифрування повинна виконуватися періодично або негайно у разі підозри на його компрометацію.

Порядок ротації:
1. Згенерувати новий криптографічно стійкий ключ довжиною 256 біт.
2. Розшифрувати наявні файли за допомогою старого ключа.
3. Повторно зашифрувати дані новим ключем та новими Nonce.
4. Перевірити можливість розшифрування нових файлів.
5. Оновити значення змінної середовища `APP_ENCRYPTION_KEY_HEX`.
6. Після перевірки резервних копій безпечно знищити старий ключ відповідно до політики зберігання резервних копій.

Автоматична ротація ключів наразі не реалізована та виконується як окрема операційна процедура.

### 14.7. Резервне копіювання та відновлення

Зашифровані файли гаманців та ключ шифрування повинні резервуватися окремо і зберігатися в захищених місцях.

Для відновлення гаманця необхідні:
- Зашифрований файл гаманця.
- Відповідний ключ шифрування.

Втрата ключа шифрування унеможливлює відновлення приватного ключа із зашифрованого файлу.

Резервні копії не повинні додаватися до Git-репозиторію або передаватися неавторизованим особам.

### 14.8. Тестування криптографічного захисту

Реалізація AES-256-GCM покривається автоматизованими модульними тестами:

- Успішне шифрування та розшифрування.
- Відхилення зміненого шифротексту.
- Відхилення некоректної довжини Nonce.
- Успішне шифрування та розшифрування файлів.
- Відхилення неправильного ключа шифрування.

Для перевірки безпеки проєкту використовуються команди:

- `cargo test`
- `cargo check`
- `cargo clippy`
- `cargo fmt --check`
- `cargo audit`

Усі зміни політики повинні фіксуватися у Git із відповідним оновленням версії документа.

У разі суперечності між документами проєкту застосовується більш сувора безпекова вимога до моменту їх узгодження.

Відповідальність за актуальність політики безпеки покладається на власника проєкту.
