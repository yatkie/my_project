## Purpose

Метою документа є визначення безпекових вимог до програмного проєкту SolanaTokenManager на основі політики безпеки, політики конфіденційності та результатів моделювання загроз за методологією STRIDE.

Вимоги спрямовані на забезпечення:

- Конфіденційності приватних ключів.
- Цілісності транзакцій.
- Автентичності компонентів системи.
- Контролю повноважень.
- Доступності програмного забезпечення.
- Безпечної взаємодії з мережею Solana.
- Захисту процесу розробки.

## Scope

Безпекові вимоги поширюються на:

- Вихідний код SolanaTokenManager.
- Генерацію криптографічних ключових пар.
- Створення та ініціалізацію SPL-токенів.
- Випуск та переказ токенів.
- Формування та підписання транзакцій.
- Взаємодію з RPC-серверами.
- Локальну конфігурацію.
- Зовнішні програмні залежності.
- GitHub-репозиторій.
- Процеси розробки та тестування.

## Requirement Classification

Для визначення пріоритетності вимог використовується така класифікація:

| Priority | Description |
| --- | --- |
| Critical | Обов'язкова вимога, невиконання якої може призвести до компрометації ключів або втрати цифрових активів. |
| High | Вимога, невиконання якої може спричинити суттєве порушення безпеки системи. |
| Medium | Вимога, спрямована на зменшення ризиків та підвищення надійності системи. |
| Low | Додаткова вимога для вдосконалення безпеки. |

## 1. Authentication and Authenticity

Вимоги цієї категорії спрямовані на протидію загрозам Spoofing.

| ID | Requirement | Priority | DFD Elements | Verification |
| --- | --- | --- | --- | --- |
| SR-01 | Застосунок повинен використовувати довірені RPC-сервери. | High | E2, P3 | Перевірка RPC-конфігурації. |
| SR-02 | Віддалені RPC-з'єднання повинні використовувати HTTPS із перевіркою TLS-сертифікатів. | High | E2, F10, F11 | Тестування з'єднання з недійсним сертифікатом. |
| SR-03 | Перед виконанням транзакції необхідно перевіряти обрану мережу Solana. | High | E3, D2, F9 | Тестування конфігурацій Devnet та Mainnet. |
| SR-04 | Для підписання транзакцій необхідно використовувати відповідні криптографічні ключі. | Critical | E1, P2, D1 | Перевірка підписів та відповідності публічних ключів. |

## 3. Accountability and Non-Repudiation

| --- | --- | --- | --- | --- |

## 7. Secure Development Requirements

Вимоги цієї категорії визначають правила безпечної розробки та супроводу програмного забезпечення.

| ID | Requirement | Priority | Verification |
| --- | --- | --- | --- |
| DR-01 | Секретні конфігураційні файли повинні виключатися з Git за допомогою `.gitignore`. | Critical | Перевірка `.gitignore` та файлів репозиторію. |
| DR-02 | Обліковий запис GitHub розробника повинен бути захищений двофакторною автентифікацією. | High | Перевірка налаштувань GitHub. |
| DR-03 | Зовнішні залежності повинні отримуватися з довірених джерел. | High | Перевірка `Cargo.toml` та джерел залежностей. |
| DR-04 | Залежності повинні перевірятися на наявність відомих вразливостей. | High | Виконання `cargo audit`. |
| DR-05 | Файл `Cargo.lock` повинен зберігатися у репозиторії. | High | Перевірка структури репозиторію. |
| DR-06 | Перед інтеграцією змін необхідно виконувати статичний аналіз та тестування. | High | Виконання `cargo check`, `cargo clippy`, `cargo test`. |
| DR-07 | Для розробки та тестування необхідно використовувати тестові ключові пари та Solana Devnet. | High | Перевірка тестової конфігурації. |
| DR-08 | ШІ-агентам забороняється передавати реальні приватні ключі та інші секретні дані. | Critical | Перевірка процесу використання ШІ-інструментів. |
| DR-09 | Виявлені вразливості повинні реєструватися та усуватися відповідно до політики безпеки. | High | Перевірка записів про вразливості. |
| DR-10 | Модель загроз та безпекові вимоги повинні оновлюватися після суттєвих змін архітектури. | Medium | Перевірка актуальності документації. |

## 8. STRIDE Traceability Matrix

Таблиця визначає відповідність безпекових вимог категоріям STRIDE.

| STRIDE Category | Security Requirements |
| --- | --- |
| Spoofing (S) | SR-01, SR-02, SR-03, SR-04 |
| Tampering (T) | SR-05, SR-06, SR-07, SR-08, SR-09, SR-10, SR-11, SR-12 |
| Repudiation (R) | SR-13, SR-14, SR-15 |
| Information Disclosure (I) | SR-16, SR-17, SR-18, SR-19, SR-20, SR-21, SR-22, SR-23 |
| Denial of Service (D) | SR-24, SR-25, SR-26, SR-27, SR-28 |
| Elevation of Privilege (E) | SR-29, SR-30, SR-31, SR-32 |

Вимоги безпечної розробки DR-01 - DR-10 є додатковими організаційними та технічними заходами захисту.

Одна безпекова вимога може одночасно зменшувати ризики декількох категорій STRIDE.

## 9. Security Verification

Для перевірки виконання безпекових вимог використовуються такі методи:

| Verification Method | Description |
| --- | --- |
| Code Review | Ручна перевірка вихідного коду. |
| Static Analysis | Статичний аналіз програмного коду. |
| Unit Testing | Перевірка окремих функцій та компонентів. |
| Integration Testing | Перевірка взаємодії компонентів системи. |
| Negative Testing | Перевірка поведінки системи при некоректних вхідних даних. |
| Dependency Audit | Перевірка зовнішніх залежностей на відомі вразливості. |
| Configuration Review | Перевірка налаштувань застосунку та середовища розробки. |
| Devnet Testing | Перевірка операцій у тестовій мережі Solana. |

Основні команди перевірки Rust-проєкту:

```bash
cargo check
cargo fmt --check
cargo clippy
cargo test
cargo audit
```

Для виконання `cargo audit` необхідно попередньо встановити відповідний інструмент Cargo.

## 10. Implementation Status

Для контролю виконання безпекових вимог використовуються такі статуси:

| Status | Description |
| --- | --- |
| Planned | Вимога визначена та запланована до реалізації. |
| In Progress | Вимога перебуває на етапі реалізації. |
| Implemented | Вимога реалізована, але ще не пройшла повну перевірку. |
| Verified | Виконання вимоги підтверджено перевіркою або тестуванням. |
| Not Applicable | Вимога не застосовується до поточної реалізації. |

На момент створення документа безпекові вимоги мають початковий статус Planned.

Статус окремої вимоги може бути змінений після аналізу фактичної реалізації та проведення відповідних перевірок.

## 11. Acceptance Criteria

Програмне забезпечення може бути допущене до використання у Mainnet за таких умов:

- Усі застосовні критичні безпекові вимоги реалізовані та перевірені.
- Відсутні невиправлені критичні вразливості.
- Приватні ключі не розкриваються через вихідний код, журнали або мережеві запити.
- Параметри транзакцій перевіряються перед підписанням.
- Повноваження підписантів перевіряються.
- Помилки RPC-з'єднання коректно обробляються.
- Виконано перевірку зовнішніх залежностей.
- Виконано тестування у Solana Devnet.
- Залишкові ризики оцінені та задокументовані.
