
# SolanaTokenManager PROJECT POLICY

> Політика розробки програмного проєкту для створення та управління SPL-токенами в мережі Solana. Визначає архітектурні принципи, правила написання коду, безпеку, тестування та документування. Політика відображає поточну реалізацію та цільові вимоги подальшого розвитку системи.

## Project Overview

**Project Name:** SolanaTokenManager

**Technical Stack:**
- Programming Language: Rust
- Blockchain: Solana
- Token Standard: SPL Token
- Build System: Cargo
- RPC Interface: Solana RPC Client
- Documentation: Markdown
- Version Control: Git

**Project Purpose:**

Створення програмного рішення для автоматизації операцій із SPL-токенами в мережі Solana.

Основні можливості:
- Створення токенів.
- Ініціалізація токенів.
- Випуск токенів.
- Переказ токенів між гаманцями.
- Підготовка до інтеграції з Pump.fun.

## Architecture Policy

Проєкт повинен розвиватися відповідно до принципів модульної архітектури.

### Architectural Principles

- Separation of Concerns — кожен модуль відповідає за окрему область функціональності.
- Single Responsibility Principle — кожен компонент повинен мати одну основну відповідальність.
- Encapsulation — внутрішня логіка компонентів не повинна бути доступною без необхідності.
- Dependency Inversion — бізнес-логіка не повинна безпосередньо залежати від деталей інфраструктури.
- Reusability — повторно використовувані операції повинні бути винесені в окремі компоненти.

my_project/

## Domain-Driven Design Policy

Під час подальшого розвитку системи рекомендується використовувати принципи Domain-Driven Design.

### Domain Layer

Повинен містити:
- Основні доменні сутності.
- Value Objects.
- Бізнес-правила.
- Domain Policies.
- Domain Events.

### Application Layer

Повинен відповідати за:
- Організацію бізнес-процесів.
- Виклик доменних сервісів.
- Управління операціями створення токенів.

### Infrastructure Layer

Повинен містити:
- Solana RPC Client.
- Інтеграцію з SPL Token Program.
- Роботу з транзакціями.
- Інтеграцію із зовнішніми API.
- Налаштування підключення до мережі.

## Coding Standards

### Naming Conventions

| Element | Convention | Example |
|---|---|---|
| Modules | snake_case | `token_manager` |
| Functions | snake_case | `create_token` |
| Variables | snake_case | `token_amount` |
| Constants | SCREAMING_SNAKE_CASE | `SOLANA_RPC_URL` |
| Types | PascalCase | `TokenManager` |
| Traits | PascalCase | `TokenProvider` |
| Enums | PascalCase | `TokenStatus` |

### Code Formatting

- Використовувати стандартний форматувальник Rust `rustfmt`.
- Дотримуватися єдиного стилю оформлення коду.
- Використовувати зрозумілі назви змінних та функцій.
- Уникати дублювання коду.
- Коментувати складні алгоритми та бізнес-правила.
- Не залишати невикористаний код без пояснення.

### Code Quality

- Використовувати типізацію Rust для контролю коректності даних.
- Уникати необґрунтованого використання `unwrap()` та `expect()`.
- Не ігнорувати результати виконання транзакцій.
- Перевіряти вхідні параметри перед виконанням операцій.
- Використовувати `Result` для обробки помилок.

## Dependency Policy

Зовнішні бібліотеки повинні підключатися через Cargo.

Основні технологічні залежності проєкту:

| Dependency | Purpose |
|---|---|
| `solana-client` | Взаємодія з RPC-інтерфейсом Solana. |
| `solana-sdk` | Робота з ключами, адресами та транзакціями. |
| `spl-token` | Операції зі SPL-токенами. |
| `spl-associated-token-account` | Робота з Associated Token Accounts. |

Правила управління залежностями:

- Використовувати перевірені бібліотеки.
- Фіксувати версії залежностей у `Cargo.toml`.
- Не додавати бібліотеки без необхідності.
- Перевіряти сумісність залежностей між собою.
- Зберігати `Cargo.lock` у репозиторії для застосунку.
- Регулярно перевіряти залежності на відомі вразливості.

## Security Policy

Безпека є одним із головних пріоритетів системи, оскільки програма працює з криптографічними ключами та фінансовими операціями.

### Wallet Security

- Приватні ключі не повинні зберігатися безпосередньо у вихідному коді.
- Заборонено публікувати приватні ключі у GitHub.
- Секретні дані повинні зберігатися в захищеному середовищі.
- Перед підписанням транзакцій необхідно перевіряти параметри операції.
- Необхідно обмежувати доступ до файлів гаманців.

### Transaction Security

- Перевіряти адресу одержувача.
- Перевіряти кількість токенів перед переказом.
- Перевіряти достатність коштів для комісій.
- Перевіряти результати виконання транзакцій.
- Не повторювати фінансову операцію без перевірки попереднього результату.
- Використовувати безпечне підтвердження транзакцій.

### Network Security

- Використовувати довірені RPC-сервери.
- Перевіряти правильність мережі перед виконанням операцій.
- Не передавати секретні дані через незахищені канали.
- Враховувати можливість помилок мережевого з'єднання.

## Error Handling Policy

Усі операції взаємодії з блокчейном повинні передбачати обробку помилок.

Основні категорії помилок:

| Error | Description |
|---|---|
| RPC Connection Error | Помилка підключення до RPC-сервера. |
| Invalid Public Key | Некоректна адреса гаманця або токена. |
| Insufficient Funds | Недостатньо коштів для виконання операції. |
| Transaction Error | Помилка виконання транзакції. |
| Token Initialization Error | Помилка ініціалізації токена. |
| Transfer Error | Помилка переказу токенів. |

Правила:
- Не використовувати безконтрольне завершення програми через `unwrap()`.
- Повідомлення про помилки повинні бути зрозумілими.
- Критичні помилки повинні зупиняти відповідну операцію.
- Помилки повинні передаватися між рівнями програми через `Result`.

## Testing Policy

Тестування повинно перевіряти правильність роботи основних операцій системи.

### Unit Testing

Перевіряються:
- Перевірка адрес публічних ключів.
- Коректність кількості токенів.
- Перевірка параметрів переказу.
- Перевірка бізнес-правил.

### Integration Testing

Перевіряються:
- Підключення до Solana RPC.
- Створення токена.
- Ініціалізація токена.
- Випуск токенів.
- Переказ токенів.

### Testing Rules

- Тестування не повинно використовувати реальні кошти без необхідності.
- Для тестових транзакцій рекомендується використовувати Solana Devnet.
- Перед використанням Mainnet необхідно перевіряти результати тестування.
- Кожна нова функція повинна супроводжуватися відповідними тестами.

## Git Workflow Policy

Для управління версіями використовується Git.

### Commit Naming

Повідомлення комітів повинні мати зрозумілий опис змін.

Основні префікси:

| Prefix | Purpose |
|---|---|
| `[FEATURE]` | Додавання нової функціональності. |
| `[FIX]` | Виправлення помилок. |
| `[DOCS]` | Зміни документації. |
| `[REFACTOR]` | Рефакторинг коду. |
| `[TEST]` | Додавання або зміна тестів. |

### Git Rules

- Не завантажувати приватні ключі до репозиторію.
- Не додавати тимчасові файли та секретні дані.
- Перед комітом перевіряти зміни.
- Використовувати зрозумілі повідомлення комітів.
- Документацію оновлювати разом зі змінами функціональності.

Основні документи:

## Anti-Patterns

У проєкті не допускається:

- Зберігання приватних ключів у відкритому коді.
- Виконання транзакцій без перевірки параметрів.
- Ігнорування помилок RPC.
- Безконтрольне використання `unwrap()`.
- Дублювання бізнес-логіки.
- Змішування всіх компонентів системи в одній функції.
- Використання неперевірених зовнішніх API.
- Опис нереалізованих можливостей як завершених.
